步驟 1（工作卡 §3-1）：超過 maxBlock 時「現行路徑」的 file:line 說明（修前）
------------------------------------------------------------------------------

修前 src/effects/EffectChain.h（git HEAD 98f346f 版本，行號為修前行號）：

  L35   void prepare (double sampleRate, int maxBlockSize = 2048)
  L43       maxBlock = juce::jmax (16, maxBlockSize);
  ...
  L108  void processBlock (juce::AudioBuffer<float>& buffer)
  L123      int numSamples  = buffer.getNumSamples();
  ...
  L129-135  // IR mode replaces the algorithmic reverb with convolution. Fall back
            // to algorithmic when no IR is loaded, and skip IR on any block larger
            // than the prepared maximum (never allocate on the audio thread).
            const bool irMode = pReverbMode != nullptr
                             && pReverbMode->load() >= 0.5f
                             && hasImpulseResponse()
                             && numSamples <= maxBlock;

現行路徑（修前）：processBlock() 對 numSamples 完全沒有上限檢查或分塊——
它就地把整段 buffer（不論多長）逐 sample 跑過 L144 起的迴圈。唯一因
numSamples > maxBlock 而改變的是 L132-135 的 irMode 判斷式：一旦
numSamples > maxBlock，irMode 強制為 false，即使 pReverbMode 選了 IR
且 hasImpulseResponse() 為 true，也會靜默改用 L200-201 的
`if (! irMode) reverb.processStereo (left, right);`（algorithmic 路徑），
不會呼叫 L211 起的 convolution.process()，且不會有任何錯誤/警告回報給呼叫端。
這就是稽核文件 §2「K-03 超過 maxBlock 靜默換演算法」與 §4-E 舊版描述的現行缺陷。
CLI 的 ScoreRenderer 不使用 EffectChain 的 IR 分支（ScoreRenderer 只用
SimpleReverb 直接介面，見 grep 結果：EffectChain.h 只被 PluginProcessor.h 與
tests/physics_models_repro.cpp include），所以此缺陷只影響 plugin/host 執行
路徑，不影響 CLI corpus 渲染——這也是為什麼 K-03 的修法對 8/8 位元不變 GATE
是安全的（見下方 GATE 3）。

修法（見 git diff -- src/effects/EffectChain.h）：processBlock() 開頭新增
「numSamples > maxBlock 時以 maxBlock 為步長切子 block，對每個子 block 遞迴
呼叫同一個 processBlock()」，不改 irMode 判斷式本身、不改 convolution 參數、
不改 reverb 演算法——只是讓每次真正執行到 L132 判斷式的 numSamples 保證
<= maxBlock，讓該判斷式的「skip IR on any block larger than maxBlock」分支
在实際執行中不再被觸發（結構仍留著，作為防禦性 fallback）。

CMakeLists.txt 變更說明（超出工作卡 GATE 5 原列清單，特此標註供稽核核實）
------------------------------------------------------------------------------

工作卡 GATE 5 原列的預期 diff 範圍是 src/effects/EffectChain.h、
tests/audit_repro.cpp、裁決包、稽核文件四項，未列 CMakeLists.txt。
但 tests/audit_repro.cpp 新增的 `#include "effects/EffectChain.h"` 會無條件
拉入 `<juce_dsp/juce_dsp.h>`（EffectChain 內有一個
`juce::dsp::Convolution convolution;` 成員，不論 reverb 模式為何都會被建構），
而 juce_Convolution.cpp 裡有非 template 的實作（建構子/loadImpulseResponse/
process 等），不掛進該 module 就沒有這些符號，連結會失敗。
TsukiSynthAuditTest 原本沒有連結 juce::juce_dsp（其他三個既有測試 target 裡，
只有 TsukiSynthPhysicsModelsTest / TsukiSynthSpectrumViewTest 有連結）。

因此在 CMakeLists.txt 的 TsukiSynthAuditTest target 新增一行
`juce::juce_dsp`（連同一段說明註解），這是讓工作卡 2.1 節指定的測試設計
（EffectChain + 真實 convolution IR）能夠編譯連結的必要條件，不是新增
CMake target（維持工作卡「不要新增 CMake target」的限制），也不影響 CI yaml。
若稽核認為這個變更超出授權範圍，請於 findings 中標出，工兵可回退並改用其他
方式驗證 K-03（例如改測 SimpleReverb 直接介面而非 EffectChain，但那樣就
測不到 EffectChain::processBlock() 本身的分塊邏輯，不符合工作卡 2.1 節的
測試設計意圖）。
