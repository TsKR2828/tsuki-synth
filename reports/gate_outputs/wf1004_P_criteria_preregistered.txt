Facts established by reading the source before measuring (not measurements):
  - Moonlight tongue-drum score (HostProbe Q09 case "moonlight_mvt1_tongue_drum") plays through plug-in engine index 1 =
    Chromatic (chr_sub_engine 0 = Tongue Drum), i.e. the `chromaticSynth` juce::Synthesiser (ChromaticSound/ChromaticVoice).
    Engine 0 (Cimbalom) and engine 3 (Piano) share `cimbalomSynth`; engine 2 (FM Piano) uses `fmPianoSynth`.
  - The pool size lives in src/PluginProcessor.cpp: three `for (i < kVoicePoolSize)` addVoice loops (WF1003-V made them one
    shared constant). The CLI target compiles only src/cli/RenderApp.cpp (CMakeLists.txt:150-170) and has no pool.
  - The pre-existing evidence from WF1003-V is the baseline: Piano pool 16 fully loaded (32 distinct notes held) p99 10.5 ms,
    4-6 blocks >= budget per round. This card RE-MEASURES that baseline in the same runs; V-card numbers are context only.

Block budget = kBlockSize / kSampleRate = 512 / 48000 Hz = 10.6667 ms (HostProbe's own block size and rate).
"violating block" = a block whose processing time >= budget.

Measured with HostProbe's existing Q09 machinery (twin = in-process juce::Synthesiser wired exactly like the processor
constructor; twin output must be sample-identical to the VST3 for the pool size the VST3 was built with; timing = wall time of
renderNextBlock() per block, 5 fresh repeats per case per pool, plus the real VST3 binary's processBlock() with the full effect chain).
Rounds: 3 HostProbe runs on the candidate build (per-engine pool) and 3 on the baseline build (all engines 16), alternating.
Machine = dev box (Ryzen 5 3500X); absolute ms do not transfer, the comparison to the Piano-16 baseline measured in the SAME run does.

      Steal counts are deterministic (same in every round). Measured via the twin tied to the binary (identity max|VST3-twin| = 0
