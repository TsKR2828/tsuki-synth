發現 1（工具層，重要）：melody_verify 的音高判定會被殘響帶偏，最大 ~9.5 cents
================================================================================
帶殘響版 122 個 FAIL 中，100 個在乾聲版消失。全部是「音高超出 5 cents」型，
而且同一音名的偏差值完全相同（E4 全部 52 顆 -9.47c、A#2 全部 18 顆 +7.93c）。

三層排查（每層皆親自執行）：
 (1) 起音誤差全部落在 ±3 ms（容差 ±10 ms）——不是時間問題。
 (2) 獨立量測（1 s 穩態段、2^22 點補零 FFT、拋物線內插）：
       E4  宣告 329.6276 Hz → 實測 329.6220 Hz = -0.03 cents
       A#2 宣告 116.5409 Hz → 實測 116.5411 Hz = +0.00 cents
       C4（對照 PASS）                         = -0.01 cents
     引擎音高正確到 0.03 cents，不是引擎問題。
 (3) 同一顆音、同一支 melody_verify，只差有無殘響：
       帶殘響 -9.48 cents → FAIL ／ 無殘響 -0.02 cents → PASS
機制：melody_verify.py:487 用頻帶（±3%）內振幅加權質心 f=Σ(f·|X|)/Σ|X| 判音高。
殘響為梳狀濾波（SimpleReverb），其響應在該窄帶內有斜率，把質心整體拉偏；
拉偏量隨頻率固定 → 同一音名永遠同一偏差。用相同公式、相同頻帶但高解析度重算，
E4 質心為 -0.02 cents，證明不是質心慣例本身的問題，而是解析度/著色所致。

*** 這個偏差本來就存在於現行 melody_verify GATE，不是本工具引入。***
以往密集段幾乎全數拒答故未浮現。任何帶殘響 score 的音高判定都帶此偏差，
而容差僅 5 cents。建議另立卡處理（本檔不擅自修改 melody_verify，R2）。

=> 直接後果：分軌驗證應在乾聲上進行（殘響是混音後的線性級，不屬音符內容）。

【先講結論】

1. 「逐事件乾聲分軌 + 線性疊加證明」作為密集複音的拆解方法，方向合理，
   而且這首曲子的實測疊加殘差有充分餘裕；這一段可以保留。

2. 現行 `melody_verify` 的逐軌音高法只適合「基頻可量、單音、乾聲」的案例。
   它以基頻附近 ±3% 頻帶的振幅質心代表音高；對弱基頻／missing-fundamental
   類型的高音鋼琴、低音起音、以及帶殘響後的頻譜著色都不穩健。

3. 現行 `stem_verify` **沒有實測泛音／partials 的頻率或振幅**。它只把
   `--dump-modes` partials 用來預判「別顆音的 partial 是否污染基頻帶」。所以目前
   可以主張「逐事件起音／基頻帶音高（在可量域）」，不能主張「泛音已驗證」。

4. 乾聲結果不應只報 671 PASS / 22 FAIL / 212 UNVERIFIED。分開主張後是：
     - 音高數字：883/905 顆取得量測，883/883 全在 ±5 cents，最大 |偏差| 2.4266 c。
     - 起音數字：671/905 顆取得精測且全在 ±10 ms，最大 |偏差| 6.9272 ms。
     - 起音拒答：212 顆，全部是 f0 < 167 Hz 的低音解析度限制。
     - 起音 FAIL：22 顆高音，基頻帶未出現足夠 rise；不能據此直接說「音高錯」。
   把兩個維度壓成一個 verdict，會把「音高已量到、起音沒量到」誤看成整顆音沒驗。

5. ±5 cents 是本專案既有、經裁定的產品門檻，不是 ISO 或業界通用標準。
   它可以保留（本次沒有改容差），但量測器本身應先用合成哨兵證明誤差 ≤1 cent，
   才能用來執行 ±5 cents 的產品 GATE。

6. 鋼琴 partial 不可一律驗成 n*f0。真實鋼琴弦有 stiffness inharmonicity；應驗
   `f_n = n F0 sqrt(1 + B n^2)` 或直接驗 `--dump-modes` 預測的逐 partial 頻率，
   並另用獨立公式／參考琴資料查 `B` 的物理合理性。

7. 目前可接受的發布措辭是「給愛麗絲 score、模態表、渲染決定性、逐軌疊加已驗；
   乾聲 883 顆有音高證據，其中 671 顆另有起音證據」。目前**不可**寫成
   「905 顆音高與泛音全部驗過」；22 顆高音的 harmonic-aware 音高／起音，以及
   所有事件的逐 partial 頻率／振幅 GATE 尚未補齊。

================================================================================
三、現行量測法逐點審查
================================================================================

【1. 分軌策略：合理】

`stem_verify.py:109` 先拒絕 layered 與 distortion；`:272` 強制未 normalize；
`:410` 把同一個 stem WAV 交給既有 `melody_verify`；`:452` 做疊加比較；`:480`
用 N * half-LSB 建 24-bit rounding 上界。對本 score（單層、distortion=0、delay=0、
reverb 為固定係數 LTI）而言，拆成事件後再相加有明確數學基礎，實測也成立。

【2. 乾聲作音準主判：合理，但要保留 post-FX 證據】

固定係數 LTI reverb 不會搬移輸入 sinusoid 的頻率位置，但會改各頻率振幅／相位；
因此它能把窄帶的「振幅質心」推動數 cents，而不代表引擎的 mode frequency 變了。
本首同一音名固定偏移、乾聲後 100 個 pitch FAIL 全消失，符合此機制。

建議契約：
  - 音準／partials 頻率在 analysis-dry stem 判。
  - 正式 wet 成品仍做疊加、效果設定／程式路徑、頻率不新增的 post-FX sanity check。
  - 不再拿 wet 窄帶質心直接執行 ±5-cents GATE。

【3. ±3% 是搜尋帶，不是允收門檻】

`melody_verify.py:92/177` 的 ±3% 換算約為 +51.173 / -52.732 cents；真正 verdict
仍在 `:489` 以 ±5 cents 判，所以目前沒有把 ±3% 誤當 PASS 容差。

但 onset STFT 是 Hann/2048 @48k（`:107`），bin 寬 23.4375 Hz。A2=110 Hz 的
整個 ±3% 帶只有 6.6 Hz，程式因 band 比一個 bin 還窄而退化成「只拿最近一格」。
這就是低音被設計成 f0<167 Hz 一律拒絕精測的根本解析度限制，不是低音真的沒有起音。

【4. 頻譜質心不是通用 F0 estimator】

`melody_verify.py:469-486` 取 t+20ms 到 t+1.25s、Hann、在基頻 ±3% 內用
`sum(f*|X|)/sum(|X|)`。優點是決定性、對已知且強的單一 peak 很便宜；缺點是：
  - reverb/EQ 的頻帶斜率會改質心；
  - 多弦 beating 與每弦振幅不平衡會改質心；
  - 基頻弱時，onset 在抵達 pitch 計算前就 FAIL；
  - 它不利用第二、第三 partial，因此與人耳的 missing-fundamental pitch 不同；
  - `--dump-modes` amplitude-weighted course_f0 和渲染共用模型振幅，單獨使用會偏向
    implementation self-consistency，必須與 score/ET 的獨立 anchor 串成兩段證據。

本專案其實已有較好的第一段：`verify_score.py:MODE_F0_TOL_CENTS` 把 dump course_f0
對 ET 判 ±5c；本首 max 2.482c。建議 stem JSON 明確同時保存：
  authored_et_hz、dump_course_hz、audio_estimate_hz、
  dump_vs_et_cents、audio_vs_dump_cents、audio_vs_et_cents。
目前只存 expected_f0_hz（dump）與 audio_vs_dump，證據鏈不夠一眼可見。

【5. 2^22 zero-padding 的文字要精確】

本檔前段的獨立探針用 1s 真實資料 + 2^22 零補點 FFT。零補點會把既有 DTFT
主瓣做更密的 spectral interpolation，方便抓 peak；它不會創造超過 1s 觀測窗的
真正解析力。Julius O. Smith 的《Spectral Audio Signal Processing》明確把它描述為
interpolating spectral peaks。故該探針的 -0.03c 數字可作輔助，但必須另以不同窗長、
phase、振幅、partial 配比的合成哨兵校準，不能只因 FFT 點數大就稱「高解析度真值」。

【6. 現行沒有泛音 GATE】

`melody_verify.expected_f0s()` 讀 partials；之後只在 `:354` 判「別顆 partial 是否掉進
本顆基頻帶」來決定拒答。逐 stem 的 `judge_stem()` 原封不動委派這個單基頻 judge。
沒有任何迴圈逐一量 observed partial peak，也沒有 partial 頻差 cents、SNR、prominence、
coverage 或振幅 dB 誤差。因此「泛音正確」目前是未證主張。

四、22 顆高音為何不能用「基頻帶沒 rise」直接判音高錯
================================================================================

從正式 score 與真實 `TsukiSynthCLI --dump-modes` 取四個代表事件；下列 amp 是 center
string 的 mode amp，dB 是相對第一 partial。course cents 是三弦 amplitude-weighted
course_f0 相對 score 的 `performance.frequency_hz`（ET anchor）：

  ev195 G5, ET 783.991 Hz, course 783.239153 Hz (-1.661 c)
    p1  783.991 Hz amp .00307    0.00 dB
    p2 1578.069 Hz amp .04612  +23.54 dB
    p3 2392.108 Hz amp .00401   +2.32 dB

  ev746 G6, ET 1567.982 Hz, course 1567.431525 Hz (-0.608 c)

    p1 2349.318 Hz amp .00078    0.00 dB

    p3 8032.265 Hz amp .00361  +13.31 dB

這些不是「只有基頻才代表音名」的訊號。聽覺研究確認：即使物理頻譜沒有 f0，人仍可由
partials 關係感到 missing fundamental；沒有任何單一頻率的能量與 perceived pitch 必然
一對一。故高音應用 multi-partial/template estimator；至少要求兩個合格 partial 對同一
基頻／同一 inharmonic B 給出一致解，再判音高。起音也應在多個可聽 partial band 的
總 spectral flux／包絡上量，不應只看最弱的 p1 band。

另外，鋼琴 partial 是 inharmonic。以上 p2 相對 2*p1 的 stretch：
  G5 +11.10 c；F#6 +38.51 c；G6 +43.03 c；D7 +91.94 c。
所以把它們硬對 `2*f0, 3*f0...` 會誤殺。必須對 dump 頻率或 stiff-string 公式。

【A. 標準與常用評測數字】

1. ISO 16:1975（2022 再確認仍現行）
   https://www.iso.org/standard/3601.html
   規定 treble-stave A = 440 Hz；用來 tuning/retuning 的產生器準確度 0.5 Hz。
   440 Hz 的 +0.5 Hz 約 +1.966 cents。注意：這是基準音／調音器材的要求，
   不是「每顆合成音可偏幾 cents」的完整產品驗收規範。

2. mir_eval melody/transcription 官方文件
   https://mir-eval.readthedocs.io/latest/api/melody.html
   https://mir-eval.readthedocs.io/latest/api/transcription.html
   預設 pitch tolerance = 50 cents；note transcription onset tolerance = 50 ms。
   這是 AMT 演算法評測中「音符辨識對不對」的寬門檻（半音的一半），不是樂器校音
   或數值合成器精度標準。不能拿 50c/50ms 來放寬本專案 5c/10ms。

【B. 現售商業調音器：代表的是量測精度，不是音符允收門檻】

1. BOSS TU-3 原廠規格：tuning accuracy ±1 cent
   https://www.boss.info/us/products/tu-3/

2. Peterson StroboStomp HD 原廠：accuracy 0.1 cent
   https://www.petersontuners.com/media/pdf/StroboStomp_HD_Manual_v1.1_EN.pdf

3. TC Electronic PolyTune Clip 原廠：strobe mode ±0.02 cent
   https://www.tcelectronic.com/en/products/0713-AAF

解讀：商業測量端普遍宣告 1c 或更細；所以「量測器自誤差 ≤1c、產品 PASS ±5c」是
合理的工程分層。不能反過來說商業產品的 0.1c 就要求所有自然鋼琴 partial/音高都在
0.1c；自然樂器有 stretch、unison beating、attack drift。

【C. 商業音高校正／物理鋼琴如何處理 pitch center 與 partials】

1. Celemony Melodyne 5 原廠手冊
   https://helpcenter.celemony.com/M5/doc/melodyneStudio5/en/M5tour_ToolPitch_2
   把 pitch center 稱作音符的 central emphasis / center of gravity，並以 cents 顯示
   相對 ET 偏差。這支持「音高中心不是只取最大 FFT bin」，但不等於本專案目前的
   單一窄帶質心已經是唯一正解。

   Polyphonic note assignment／overtone 官方說明：
   https://helpcenter.celemony.com/M5/doc/melodyneStudio5/en/M5tour_NA_Mode_Tools
   明說商業 polyphonic 分析也可能把 prominent overtone 誤當實際音符，或把很小聲的
   真音符誤當低音的 overtone；介面會顯示 overtone series 並允許人工改 assignment。
   這直接支持本專案 fail-closed 與分軌法，也提醒不能把黑箱轉譜當唯一 GATE。

2. Modartt Pianoteq 原廠手冊
   https://www.modartt.com/user_manual?lang=en&product=pianoteq
   說明其 piano tuning（flat temperament 除外）會考慮 string inharmonicity，像調音師
   聽 partial 間 beats；並提供 natural/harmonic stretching、unison width/balance。
   這是現售物理鋼琴產品的直接先例：鋼琴不能用所有 partial 必須恰為 n*f0 的簡化規格。

【D. 鋼琴 inharmonicity 理論與參考範圍】

Rigaud, David & Daudet, JASA 133(5), 2013, DOI 10.1121/1.4799806：
https://www.institut-langevin.espci.fr/biblio/2020/3/5/916/files/2013_a_parametric_model_and_estimation_techniques_for_the_inharmonicity_and_tuning_of_the_piano.pdf

論文給 plain stiff string：
  f_n = n F0 sqrt(1 + B n^2)
  B = pi^3 E d^4 / (64 T L^2)
  典型 B 範圍約 10^-5 到 10^-2；也明說 bridge motion 與 doublet/triplet coupling
  會讓實際 partial 偏離簡式並產生 multiple partials、double decays、beating。
  ET anchor：F_ET(m)=440*2^((m-69)/12)，tuning deviation 用 cents 表示。

用同一定義由 center-string f1/f2 反解（
  r=(f2/(2*f1))^2，B=(r-1)/(4-r)）：
  G5  B=0.004321（在上述典型範圍內）
  F#6 B=0.015398
  G6  B=0.017284
  D7  B=0.038802

後三者高於該論文列的典型上緣 0.01，尤其 D7 約 3.88 倍；這是**物理合理性警訊，
不是本查核直接宣告 bug**。高音 score 全部指定 diameter_mm=1.0，而 Acoustical Society
of America 的 Acoustics Today 鋼琴弦文章指出現代琴 extreme treble 約 0.8 mm、
低到 middle C 下方一個八度才約 1.0 mm：
https://acousticstoday.org/issues/2016AT/2016Spring/files/basic-html/page17.html

因 B 與 d^4 成正比，直徑對高 partial stretch 極敏感。建議另立物理卡，拿實際琴 scale
（逐音 L/d/T）或商業／實測 reference 驗 F#6/G6/D7；不得只為讓 stem GATE 過而改模型。

【E. 人耳不是只看物理 f0 能量】

Oxenham, “Pitch Perception” review：
https://pmc.ncbi.nlm.nih.gov/articles/PMC3481156/
說明 harmonic complex 的 pitch 通常關聯於 periodicity/F0，低階 resolved harmonics
提供較穩健準確 pitch；即使 fundamental 缺失，仍可抽取 missing-fundamental pitch。

Bendor et al. review：
https://pmc.ncbi.nlm.nih.gov/articles/PMC3098378/
明說沒有「某一個頻率的能量」與 perceived pitch 的直接一對一關係。

這是 G5/G6/F#6/D7 不能只靠 p1 onset 作最終 verdict 的理論依據。

【F. 可參考的 GitHub／開源實作】

1. librosa `yin` / `pyin` / `piptrack`
   https://github.com/librosa/librosa/blob/main/librosa/core/pitch.py
   pYIN 先產生 YIN F0 candidates/probabilities，再用 Viterbi 找最可能軌跡；
   官方建議範圍約 C2-C7，D7 已超過建議上界，所以它適合做單音 harmonic cross-check，
   不宜單獨承擔本首最高音 GATE。

2. pYIN 原作者群 Vamp plugin
   https://github.com/c4dm/pyin
   README 明確限定 monophonic、harmonic instrument。這正好說明：分軌後可用，但鋼琴
   inharmonic high register 仍需 model-aware partial template。

3. Essentia PitchYinFFT / HarmonicPeaks
   https://essentia.upf.edu/reference/streaming_PitchYinFFT.html
   https://essentia.upf.edu/reference/std_HarmonicPeaks.html
   PitchYinFFT 會輸出 confidence（官方要求 confidence=0 時不得使用 pitch）；
   HarmonicPeaks 以 spectral peaks + pitch 找逐 harmonic 頻率與振幅。可參考其資料流，
   但 TsukiSynth piano 必須把理想 harmonic 位置替換成 dump/stiff-string partial 位置。

4. Spotify Basic Pitch
   https://github.com/spotify/basic-pitch
   是 polyphonic AMT / audio-to-MIDI，適合非權威交叉檢查；本專案已有精確 stems，
   沒必要把可解釋的主 GATE 換成神經網路黑箱。

5. librosa `piptrack` 的 thresholded parabolic peak interpolation
   https://librosa.org/doc/0.10.2/generated/librosa.piptrack.html
   可直接參考 peak interpolation 寫法。Julius O. Smith 的零補點／peak interpolation 理論：
   https://www.dsprelated.com/freebooks/sasp/Zero_Padding_Interpolating_Spectral_Peaks.html


================================================================================
六、建議的可執行驗收契約（不在本次擅自改容差）
================================================================================

【Layer 0：來源真值】
  - `performance.frequency_hz` 或 note->MIDI ET 公式為獨立 authored anchor。
  - `frequency_mode=midi`：f_ET=440*2^((m-69)/12)。
  - `frequency_mode=geometry`：必須改用明列的 geometry truth，不能硬判 ET。
  - 保存 score/tool/CLI/hash、analysis-dry 衍生 diff。

【Layer 1：dump 物理／設計真值】
  - course f0 vs authored anchor：沿用 ±5c（現有 R2，不改）。
  - string piano partials：獨立用 stiff-string oracle fit B，再與 dump 比；
    B 的 10^-5~10^-2 只當一般鋼琴 sanity range，超出要 REVIEW，不可無條件 FAIL，
    因琴型、bridge、coupling、參數定義會影響。
  - beam/plate 非諧模態繼續用各自 eigenvalue ratio，不套 harmonic series。

【Layer 2：逐 stem 音訊音高】
  - primary：model-aware multi-partial peak assignment。
  - 每個 predicted partial 在寬 candidate band 中找唯一 peak，最後以 cents 判定。
  - candidate band 可沿用 ±3%（搜尋而非 PASS）；final frequency gate 沿用 ±5c。
  - 至少 2 個合格低階 partial 同意同一 pitch/B；若 p1 很弱，不把 p1 absence 當音高 FAIL。
  - 可測 p1 時，以 YIN/pYIN 或 parabolic spectral peak 作第二 estimator；不一致則 REVIEW。
  - estimator 自身合成校準：純 sine、missing-fundamental、inharmonic、不同 phase/velocity/
    T60、±4.9c PASS mutant、±5.1c FAIL mutant；目標量測誤差 ≤1c。

【Layer 3：逐 partial 存在、頻率、振幅】
  - 可直接重用 `tools/physics_verify.py` 的概念與程式：unique peak assignment、
    SNR>=20dB、prominence>=6dB、global>=-60dB、model-required floor=-45dB、coverage。
  - 但 `physics_verify` 現行 piano partial `tol_pct=3.0` 約 51 cents，對「音準」太寬；
    不可照抄為 stem final frequency tolerance。搜尋窗與 final tolerance 必須分欄。
  - partial frequency final 建議與 f0 一樣 ±5c；這是專案規格，不宣稱 ISO 標準。
  - partial relative amplitude 可沿用專案既有 ±3.0 dB；外界沒有一個跨琴型、音高、力度
    都成立的固定泛音振幅表。若要主張「像真實鋼琴」，必須另建逐音/力度 reference corpus
    與統計區間，不能拿 ±3dB 說成自然鋼琴業界標準。
  - 報告每個 partial：expected Hz、measured Hz、cents、SNR、prominence、relative dB、
    required/optional/missing/out_of_band，不能只給總 PASS。

【Layer 4：起音】
  - 保留 ±10ms（既有 R2），但把 estimator 換成「所有 model-audible partial bands 的
    合計 spectral flux／wideband transient envelope」，讓 A1/A2 等低音不受 6.6Hz 窄帶限制。
  - mir_eval 的 50ms 只能當 AMT 對照，不能用來放寬 sample-accurate renderer。
  - 音高、起音分開 verdict；一個 UNVERIFIED 不抹掉另一個已得到的 PASS 證據。

【Layer 5：mix transfer】
  - analysis-dry stems 全數入和；reference 與 stems 長度／channel／identity 完整性檢查。
  - 非線性、layered、stateful cross-event coupling 繼續 fail-closed。
  - 正式 wet score 保留目前疊加證明；另報 raw residual、量化 budget、margin。

建議最終 JSON 不是單一 event verdict，而是：
  event: {
    onset: PASS|FAIL|UNVERIFIED,
    authored_pitch: PASS|FAIL,
    audio_pitch: PASS|FAIL|UNVERIFIED,
    partial_frequency: PASS|FAIL|UNVERIFIED,
    partial_amplitude: PASS|FAIL|UNVERIFIED,
    overall: PASS only if all REQUIRED claims PASS
  }

K-02  候選 P2：algorithmic／IR reverb 的 wet gain 標度不一致
-------------------------------------------------------------------------------

  - src/effects/SimpleReverb.h:154-156：algorithmic wet 額外乘 0.15。

K-03  候選 P2：超過 prepare maxBlock 的單一 audio block 會瞬間改用另一套 reverb
-------------------------------------------------------------------------------

src/effects/EffectChain.h:129-135 明確以 `numSamples <= maxBlock` 決定 IR mode；超過時同一
參數狀態直接落入 algorithmic path。這避免 audio-thread allocation，但也讓音色依 block size
改變，且可能在邊界產生不連續。本輪 HostProbe 未注入 oversize block，需加 DSP unit test：
同一 IR、同一輸入分別以 maxBlock 與 maxBlock+1 驗證不能靜默換演算法。


K-04  候選 P3：SpectrumView 寬度 1 px 時產生 0/0
-------------------------------------------------------------------------------

src/analyzer/SpectrumView.h:193 把 w clamp 到至少 1；:200 卻除以 `(w - 1)`。
w=1 時為 0/0 → NaN，後續交給 bin/path 計算。一般 UI 尺寸通常大於 1，所以是低風險邊界，
但縮放／layout transient 或獨立 component test 可觸發，應以 w<=1 特判或分母至少 1。


K-05  候選 P3／local DoS：大型輸入缺全域資源上限
-------------------------------------------------------------------------------

ScoreParser 先 loadFileAsString，再解析 events/annotation arrays；schema 對 events、tempo_map、
time_signatures 等也沒有 maxItems。renderer 對最終 audio buffer 已有約 1 GiB budget 防線，
但 JSON parse、validation 與 dump 前仍可能被巨大本機檔耗盡記憶體／CPU。

這需要攻擊者能讓使用者／CI 驗證其 score，不是 remote unauthenticated DoS；本輪沒有為了
證明它而建立巨量檔案。建議按 CI 與桌面產品可接受規模訂 file bytes、events、layers、
annotation rows 上限，並以 near-limit/over-limit fixture 驗證。


K-06  候選 P3：部分 verifier subprocess 沒有 timeout
-------------------------------------------------------------------------------

唯讀搜尋顯示 tools/physics_verify.py 的數個 subprocess.run，以及
tools/check_piece_consonance.py:86 沒有 timeout。正常內建 probe 有界，但任意 score 或 CLI
hang 會讓 automation 無限等待。這是可用性／CI robustness，不是命令注入。

R-01  P1 / HIGH — crossplatform `--force-clean` 可經 parent symlink 刪掉整個 --emit root
-------------------------------------------------------------------------------

安全暫存重現：
  1. 建 `<out>/unrelated-at-output-root.txt`。
  2. 令 `<out>/water_gong_clamped` directory symlink 指回 `<out>` 本身。
  3. 執行 emit(..., force_clean=True)。

原始結果：
  [OK] ...water_gong_clamped.score.json -> water_gong_clamped.wav
  Wrote ...\crossplatform-parent-link\platform.json (1 score(s), 0 failure(s))
  run_exit 0
  root_sentinel_survived False
  output_root_entries ['platform.json', 'water_gong_clamped']

根因：tools/crossplatform_verify.py:205-229：
  resolved = render_dir.resolve()
  out_resolved = out_dir.resolve()
  if resolved != out_resolved and out_resolved not in resolved.parents: reject

當 symlink 恰好 resolve 成 out_resolved 本身，`resolved != out_resolved` 為 false，containment
守衛反而放行；接著 `shutil.rmtree(resolved)` 直接刪除整個 caller-owned --emit root，並重建它。

`--force-clean` help 授權的是清理「pre-existing non-empty render directory」，不是刪除它的
父輸出根與其他檔案；所以不能因使用者給了 destructive flag 就把此案例降為正常行為。

必修驗收：resolved target 必須是 out_resolved 的「嚴格子孫」且 identity 不等於 root；
最好不要 rmtree resolved target，而是拒絕任何 symlink/reparse point，或只操作由本次 marker
證明 ownership 的實體目錄。新增 parent-link、sibling-link、outside-link 三種反例。


R-02  P2 / output path escape — stem_verify 會跟隨空 stems/reference link 寫出 --out-dir
-------------------------------------------------------------------------------

案例 A：`<out>/stems` 是指向另一個空目錄的 directory symlink。

  run_exit 0, status ok
  outside_entry_count 4
  outside entries:
    ev_0000/
    ev_0000/score.json
    ev_0000/stem_stem_0000.wav
    ev_0000/stem_stem_0000.wav.render.json

案例 B：`<out>/reference` 指向另一個空目錄。

  run_exit 0, status ok
  outside_entry_count 3
  outside entries:
    score.json
    reference.wav
    reference.wav.render.json

根因：
  - tools/stem_verify.py:592-618 只有「stems 已存在且非空」時才做 resolved containment。
    空 symlink 的 `any(stems_dir.iterdir())` 為 false，直接被當作 caller-owned empty dir 使用。
  - ref_dir 沒有對 caller-owned existing link 做 containment/reparse-point guard。
  - cleanup 因 stems_dir_preexisted=True 不刪，工具仍回 status ok。

這次沒有覆寫既有檔（CLI 本身拒絕 overwrite），但能在使用者指定根目錄以外建立固定名稱
的 JSON/WAV/manifest。威脅需要本機預置 symlink/junction，故列 P2，不誇大成 remote RCE。


R-03  P3 / option-contract — keep_stems=False 仍會保留本次產生的 stems
-------------------------------------------------------------------------------

若 caller 事先建立一個「空的真實 stems 目錄」，修補將它標為非本次 ownership：

  run_exit 0, status ok
  stems_dir_survived True
  entry_count 4（score.json + WAV + manifest）

CLI help 說 `--keep-stems` 是「keep ... instead of deleting」，因此沒給此旗標通常表示不保留；
現在為了安全而保留是合理 fail-safe，但參數語意已改。較乾淨的設計是 caller out-dir 下再建
unique run child，最後只刪自己的 child，而不是讓 keep_stems=False 變成條件式。

五、功能彼此打架／參數顯示與 DSP 真相不同
================================================================================

P-01  P1 商品 recall blocker — IR mode 與 user preset 舊問題仍未修
-------------------------------------------------------------------------------

程式仍是：
  - PresetManager.h:122-152 user preset 只保存 APVTS。
  - PresetManager.h:374-383 load 只 replace APVTS state。
  - PluginProcessor.cpp:699-745 只有完整 DAW state 額外保存/載入 reverb_ir_path。
  - EffectChain.h:132-135 真正 IR 條件還需要 hasImpulseResponse()。

更直接的參數不誠實：
  - PluginEditor.cpp:642-653 只看 `fx_reverb_mode==1` 就把按鈕顯示成 `IR`。
  - UiLocale.h:254-255 tooltip 明說「IR convolution reverb」。
  - EffectChain 在沒有已載入 IR 時卻走 algorithmic fallback。

所以畫面／DAW automation lane 可以說 IR，實際 DSP 不是 IR。使用者也能在未載入 WAV 時直接
按切換鍵進入此假狀態。user preset reload 仍可能 fresh instance 退回 algorithmic、dirty
instance 沿用上一個 IR；本輪 HostProbe H5 只驗完整 DAW state，不驗 user preset asset recall。


P-02  P1/P2 DAW integration — getTailLengthSeconds 忽略物理模態長尾
-------------------------------------------------------------------------------

PluginProcessor.cpp:402-459 的 tail 只計：
  - FM release（並至少 2 秒）
  - delay repeats
  - algorithmic T60/room-size 或 IR seconds

它完全沒有讀目前 engine/material/geometry，也沒有讀 CimbalomVoice/ChromaticVoice 的 modal T60。

預設參數公式只回約：
  base 2.0000s + default algorithmic component 1.4527s = 3.4527s。

但同一實作的 fresh `physics_verify --full` 音訊實測：
  cimbalom/piano MIDI60 約 4.34–4.35s、water gong 7.47–7.48s、tongue drum 30.18s。
若 reverb mix=0，host metadata 更只剩 2s。

影響：依 `getTailLengthSeconds()` 決定 offline bounce/freeze 尾長的 DAW 可能截掉域內引擎的
可聽尾音；插件自己宣稱 T60 正確，宿主介面卻回更短數字，兩功能互相打架。

必修：以 active/max supported engine 的保守上界回報，或維護與當前 APVTS 物理參數一致的
可即時計算 modal tail；新增 reverb-off 的 Tongue/Cimbalom/Piano host-tail regression。


P-03  P2 UI collision + hidden-state sound — Custom Harmonics 與一般 Chromatic controls 打架
-------------------------------------------------------------------------------

PluginEditor.cpp:408-417：只要 eng=Chromatic，就把 exciter/strike/thickness/size/glide 全部
setVisible(true)；subengine=Custom 時又把 16 個 ratio/amp controls 設 visible。

PluginEditor.cpp:1305-1339：Custom layout 只配置 ratios/amps；一般 Chromatic layout 才配置
thickness/size/glide/strike/exciter。從 Tongue/Water 切到 Custom 時，那些仍 visible 的 controls
保留舊 bounds，會與新 harmonic grid 疊在一起或形成 stale/zero-bound 控件。

DSP 又不是單純「多出無效 UI」：
  - ChromaticEngine.h:148 對所有 subengine 讀 chr_pitch_glide。
  - :455-467 對所有 subengine 套 scaleFrequencies，沒有 subEngine==WaterGong 條件。
  - :261 對 Custom 也呼叫 setupExciter，所以 chr_exciter 仍改變 transient noise。
  - strike/thickness/size 對 Custom 主模態路徑多數不生效，成為看得到但不改主要聲音的 dead knobs。

因此 Custom 聲音可能依切換前留下的 glide/exciter 值而變，同時 UI 可能重疊。文件提案原本寫
glide 僅 Water Gong，現行 C++ 註解也稱 Water gong pitch glide，但實作沒有 domain gate。


P-04  P2 — pitch glide 的 cap 與曲線依 host block size
-------------------------------------------------------------------------------

ChromaticEngine.h:452-467 宣稱 rate independent of host buffer size；實際每 block：

  glidePhase += amount * 0.15 * numSamples/sampleRate;
  if (glidePhase < 0.5) scaleFrequencies(1 - glidePhase*0.3);

跨過 0.5 的那個 block 不會 clamp/apply 精確 0.85，而是停在前一個 block 的頻率。
48kHz、amount=1 的最壞 cap shortfall（純公式，不是聽感猜測）：

  block 64:   0.122 cents
  block 512:  0.977 cents
  block 2048: 3.906 cents
  block 8192: 15.572 cents

達 cap 前也以每 block 階梯更新。這不是「時間進度完全失速」，但最終音高確實依 buffer size，
與 sample-accurate/host-independent 主張不一致。應 clamp phase=min(0.5, phase+step) 並在 cap
那個 block 套最後值；若要真正 sample-independent glide，要在 block 內插值。


P-05  P2/P3 — Reverb 三套控制互斥，但 UI/automation 沒揭露誰正在失效
-------------------------------------------------------------------------------

EffectChain.h:129-158：
  - IR active 時 Room Size 與 T60 都不控制 reverb algorithm。
  - Algorithmic 且 T60>=0.01 時，Room Size 不生效。
  - T60<0.01 時才由 Room Size 控制。

PluginEditor 仍同時顯示 Mix/Room Size/T60，切 IR 也不 disable irrelevant knobs；IR 沒 asset
時還反向 fallback algorithmic。使用者移動一顆合法、host-visible 的 continuous parameter，
可能完全沒有聲音變化，且畫面沒有 inactive/fallback 狀態。

另有實作註解 `smooth every continuous control`，但 EffectChain.h:112-121 只 smooth comp、delay、
room size、mix、distortion；`fx_reverb_decay`、`fx_eq_freq`、`fx_eq_gain` 是 block-step 更新。
這是註解／automation 品質主張過頭，不表示目前一定 crash；需 automation discontinuity test。


P-06  P2 candidate — Algorithmic 與 IR wet gain 沒有同一標度
-------------------------------------------------------------------------------

SimpleReverb.h:154-156：algorithmic wet output 額外乘 0.15。
EffectChain.h:198-205：IR wet 直接以 m 混合，沒有 0.15。

IR 檔本身振幅與 JUCE convolution normalization 會影響實際 dB，所以本輪不捏造固定 loudness
jump；但同一 `fx_reverb_mix` 在兩 mode 不是同一 gain law，切 mode 的參數可比性沒有成立。


P-07  P2 candidate — oversize block 讓 IR mode 靜默換成 algorithmic，tail metadata 卻仍按 IR
-------------------------------------------------------------------------------

EffectChain.h:132-135 以 `numSamples <= maxBlock` 決定 IR；超過 prepare maxBlock 就切 algo。
PluginProcessor::getTailLengthSeconds 只看 mode+hasIR，不知道該 block 已 fallback，仍加 IR seconds。
這是音訊 path 與 host metadata 的另一個分歧。現有 HostProbe 沒有 IR + oversize block 組合測試。
