線性成長的具體來源：tools/stem_verify.py (HEAD 版, commit 前) run() 函式，
第 919 行 `stem_arrays = {}`，第 958 行 `stem_arrays[orig_idx] = arr_i`。

  * 這個 dict 對每一顆 velocity>0 的事件（跑到 --limit 或全部 905 顆）都存一份
    完整的 float64 ndarray（該事件單獨渲染出的 stem WAV 全部取樣點，經
    read_wav_float() 讀入，shape=[n_samples, n_channels]，dtype=float64）。
  * 這些陣列從各自被讀入的那一刻起，一路被保留到函式最後才用到的地方 --
    第 972 行 `stem_list = [stem_arrays[i] for i, _ in used if i in stem_arrays]`
    + 第 973 行 `compare_superposition(arr_ref, stem_list, ...)` -- 也就是說，
    N 顆事件的音訊陣列会同時全部活在記憶體裡，直到疊加證明算完為止。
  * 每一顆 stem 的緩衝長度＝該事件自己的 eventEndTime + 尾音 margin（見
    superposition_tail_margin_ms()），不是整首歌的長度，但 N 顆同時累加 ->
    記憶體峰值隨事件數（N）線性成長 -- 這就是本卡登記的 "905 事件全曲跑
    >28 GB" 現象的直接成因。
  * 其餘結構核對過，均非 O(event_count) 成長來源：`stem_results`（每顆事件
    只存 verdict/reason 等純量/字串的小 dict）、`rendered`（render_many() 回傳
    的只是路徑字串）、`render_many()`/`render_one()` 本身透過 subprocess 呼叫
    TsukiSynthCLI.exe 渲染，音訊資料是 CLI 子行程寫檔，不進 Python 行程記憶體。
    melody_verify.py / verify_score.py 均無模組層級快取（grep 確認，無
    lru_cache / 模組級 dict-as-cache）。

1. 修法
================================================================================

只動 tools/stem_verify.py，判定邏輯／容差／輸出 schema 一個都沒動：

  (a) 新增 read_wav_header(path)：只解析 RIFF 'fmt ' chunk 取得
      (sample_rate, n_channels)，用檔案 seek 跳過 'data' chunk 的位元組，
      從不把音訊資料讀進記憶體。用來取代 run() 迴圈內原本呼叫
      read_wav_float()（會把整段音訊讀進來）只是為了比對 sample_rate/
      channel 是否跟 reference 相容那一步 -- 現在只讀 header，不再讀值。

  (b) 新增 StemArrayStream 類別：對一串 (orig_idx, wav_path) 提供
      __len__/__iter__，行為對 compare_superposition() 而言與傳一個真正
      的 Python list 完全一樣（該函式只用 len()/for 迴圈兩種操作），
      但 __iter__ 是產生器，每次疊代才呼叫 read_wav_float() 讀入「這一顆」
      stem 的完整陣列、算進 composite 總和後即可被 GC 回收 -- 疊代順序與
      run() 原本 `[stem_arrays[i] for i, _ in used if i in stem_arrays]`
      的順序完全相同（同樣依 `used` 的順序、同樣的 in/not-in 過濾邏輯），
      所以逐樣加總的順序、因而浮點捨入結果，跟修改前逐位元相同。

  (c) run() 內：`stem_arrays = {}`（存滿陣列的 dict）改成 `stem_wav_paths = {}`
      （只存 wav_path 字串的 dict，metadata-only）；原本讀整段陣列做
      sr/ch 相容性檢查那行改呼叫 read_wav_header()；superposition 那段的
      `stem_list = [...]`（materialize 全部陣列成 list）改成先建
      `stem_entries = [(i, stem_wav_paths[i]) for ...]`（只是路徑 tuple 列表，
      非陣列）再包成 `StemArrayStream(stem_entries)` 傳給
      compare_superposition() -- 呼叫點、參數個數、下游所有 len(stem_list)/
      check_superposition_completeness()/vacuous 判斷完全不變（StemArrayStream
      支援 len()）。

  compare_superposition() 函式本身一行都沒改（只在 docstring 補充一句說明
  它現在也接受 duck-typed 的 len()+iteration 物件，不只是 list）-- 其邏輯、
  容差、輸出欄位、S1 哨兵測試涵蓋的行為完全不受影響。

  --limit / --jobs / --json / --analysis-dry 等既有介面全部原樣保留，
  未新增/移除任何 CLI 參數。
