================================================================ 1. Q12：CI 多行指令的 exit code
問題：GitHub Windows runner 的 pwsh 步驟只看最後一個指令的 exit code（runner 前加 $ErrorActionPreference='stop'，
但那只管 PowerShell cmdlet，不管 ctest/python 這類原生程式），前面的 ctest、pytest 失敗會被蓋掉。
修法（兩支 workflow 一致）：每個多行 pwsh 區塊裡，每一行原生指令後面都接
  if ($LASTEXITCODE -ne 0) { exit $LASTEXITCODE }
並在這些步驟明寫 shell: pwsh（Windows runner 本來的預設，寫出來只是讓語法歸屬清楚）。
逐一檢查全檔每個多行 run（兩檔共 14 個多行步驟：physics.yml 6 個、release-physics.yml 8 個）：
  - 補檢查的 7 個：physics.yml「Install Python dependencies」「Run spectral and T60 metrology self-tests」；
    release-physics.yml 兩個 job 的「Install Python dependencies」、「Configure and build all release targets」、
    「Run C++ and Python physics gates」、「Build pinned official Steinberg VST3 validator」（git clone／checkout／submodule／cmake -S／cmake --build 五行）。
  - 本來就對的 5 個 pwsh 步驟：兩支的 HostProbe（自己 exit $code）、整曲 smoke（$fail 迴圈）、pluginval 下載（只有 cmdlet）、
    兩個驗證器（呼叫 tools/validate_plugin.ps1，失敗時 throw）。另外 ASan 那步是單行（呼叫 tools/run_asan_ctest.ps1，失敗時 throw）。
  - 2 個 bash 步驟：Linux「Install JUCE build dependencies」原本不寫 shell（Linux 預設 bash -e，本來就會停），改成明寫 shell: bash
    （runner 用 bash --noprofile --norc -eo pipefail）；跨平台比對那步原本就是 shell: bash，裡面刻意 set +e 取 exit code 再 set -e，沒改。
HostProbe 次序：
  - physics.yml：HostProbe＋log 上傳移到 build-and-verify 的最後（ctest、pytest＋--selftest、T60、--full、整曲 smoke、協和度都在它前面）。
  - release-physics.yml：HostProbe＋log 上傳移到 build job 最後（物理 gate、pluginval、Steinberg validator、CLI 上傳之後）；
    build job 加 outputs.cli_uploaded = ${{ steps.upload_cli.outcome == 'success' }}，corpus job 加
    if: ${{ !cancelled() && needs.build-and-host-validate.outputs.cli_uploaded == 'true' }}，
    所以 HostProbe 失敗時 corpus 分片照跑（整條 workflow 還是紅），CLI 上傳前任何失敗照舊跳過 corpus。
  - 兩支 workflow 的 HostProbe 註解「working directory MUST be the repo root」改成現況：cwd → TSUKI_REPO_ROOT →
    exe 所在資料夾往上找，會印出用了哪條；都找不到 H8 會大聲 FAIL；仍建議在 repo 根執行（步驟本身照舊用 repo 根）。
驗證：YAML 解析＋靜態檢查改前 FAIL（7 步）→ 改後 PASS；照 runner 包法本機模擬 30 個「只讓一個指令失敗」情境，
改前 12 個被蓋掉（exit 0）→ 改後 0 個；全部成功時整步照樣 exit 0。

(b) stem_verify.read_wav_float 支援 WAVE_FORMAT_EXTENSIBLE（0xFFFE）：依 SubFormat GUID 判斷——KSDATAFORMAT_SUBTYPE_PCM → 當 tag 1、
    _IEEE_FLOAT → 當 tag 3，然後完全照原本的解碼（PCM 16/24/32、float 32；有效位元左對齊在容器裡，所以除數一樣）。
    大聲丟錯（ValueError）的情況：GUID 不是這兩種（含第一欄是 1 但後段不是 KSDATAFORMAT 的廠商 GUID）、fmt 不到 40 bytes、
    cbSize < 22、wValidBitsPerSample 大於容器、64-bit float 等原本就不支援的格式。
    另外順手修一個讀取邊界：fmt chunk 現在只讀自己的 bytes（原本固定讀 16 bytes，fmt 比 16 短時會讀到下一個 chunk），
    fmt 不到 16 bytes 改丟 ValueError「truncated fmt chunk」（跟 read_wav_header 同一句）。正常檔案結果不變。
    GUID 常數出處：Microsoft mmreg.h／ksmedia.h 的 KSDATAFORMAT_SUBTYPE_PCM／_IEEE_FLOAT = {0000000X-0000-0010-8000-00AA00389B71}
    （檔案格式規格，不是物理常數；test_stem_stream.py 原本就有同一組 GUID 尾碼）。
    既有測試 test_stem_stream.py::test_header_extensible_fmt 原本「釘住」舊行為（read_wav_float 拒絕 EXTENSIBLE），
    本卡照 O16 改行為，所以把它改成新行為（同一個檔要讀出跟一般 PCM16 逐樣本相同的值），測試名稱保留；「不支援就大聲失敗」
    的性質改由新的 test_extensible_*_refused 系列保住。
