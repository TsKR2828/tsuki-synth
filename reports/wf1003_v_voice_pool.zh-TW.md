# WF1003-V：外掛 voice pool 16 要不要加大到 32（證據門檻制）

> 日期：2026-10-03　卡：WF1003 V 卡　狀態：**結論＝維持 16**（32 沒有通過事先寫好的判準）
> 裁決依據：月月 2026-10-03「照 Fable 的建議」＝證據門檻制：32 只有在「沒有即時違規、處理時間餘裕仍足、搶音明顯下降」同時成立時才採用。
> 判準在量測**之前**寫好：`reports/gate_outputs/wf1003_V_criteria_preregistered.txt`（檔案時間 12:56；第一次正式量測 13:01 才開始）。
> 量法與重跑指令：`reports/gate_outputs/wf1003_V_method.txt`。全部原始輸出：`reports/gate_outputs/wf1003_V_raw_*.txt`。
> 月月是聾人使用者，以下全部是數字，沒有任何聽感判斷。

## 0. 一句話

加大到 32 之後，真的會用到 20 顆的月光舌鼓版**搶音從 64 次降到 0 次，而且處理時間幾乎沒變**；
但 32 顆 Piano 同時響的最壞情形，處理一個區塊平均要 **7.3 ms、p99 要 20.5 ms，超過 10.67 ms 的即時預算**（16 顆時平均 2.4 ms、p99 10.5 ms）。
判準第二條（沒有即時違規）在這個最壞情形不過，所以維持 16。

## 1. 先查的兩件事

| 問題 | 答案 | 出處 |
|---|---|---|
| voice pool 常數在哪 | `src/PluginProcessor.cpp` 建構子裡三個 `for (int i = 0; i < 16; ++i)`（Cimbalom／Chromatic／FM 各一個 `juce::Synthesiser`；Piano 與 Cimbalom 共用第一個）。本卡把三個字面 16 換成同一個具名常數 `kVoicePoolSize`（值仍是 16，可用編譯參數 `TSUKI_VOICE_POOL_SIZE` 覆寫，只為了能重跑這次證據） | `src/PluginProcessor.cpp` 檔頭與三個迴圈 |
| CLI 渲染會不會受影響 | **不會**。CLI 這個 target 只編 `src/cli/RenderApp.cpp`（`CMakeLists.txt:150-170`），`PluginProcessor.cpp` 只編進外掛 target（`CMakeLists.txt:124`）；`src/score`、`src/cli` 裡沒有 `Synthesiser` 也沒有 `PluginProcessor`，CLI 是每個事件自己 new 一顆 voice、沒有 pool。所以 75 首 WAV 位元不可能因這張卡改變，不必停手 | `grep` 結果與 `wf1003_V_method.txt` 末段 |

## 2. 判準（量測前寫好，原文見 `wf1003_V_criteria_preregistered.txt`）

| 編號 | 條件（全部成立才採用 32） | 性質 |
|---|---|---|
| C1 | 月光舌鼓版搶音次數：32 的次數 ≤ 16 的次數的一半 | 本卡的決策規則，不是 GATE 容差，不進 ROADMAP §6 |
| C2 | **沒有即時違規**：任何一個區塊的處理時間 ≥ 該區塊的即時預算（512 / 48000 Hz = **10.667 ms**），算違規；32 在 (a)月光 (b)給愛麗絲 (c)32 顆同時發聲的壓力測試（Chromatic 與 Piano 各一）(d)用 32 建出來的真 VST3 跑月光，**每一次重複都必須 0 個違規區塊** | 違規的定義是「來不及」，不是調出來的數字 |
| C3 | 餘裕：上述所有情形最慢的一個區塊 ≤ 預算的一半（5.333 ms） | 本卡的決策規則（「至少留 2 倍餘裕」），不進 §6 |
| C4 | 16 顆本來就夠的曲子，32 不能改變輸出（給愛麗絲：兩種 pool 的輸出逐樣本相同）；CLI 不共用 pool 常數，否則停手 | 無新常數 |

## 3. 量了什麼、怎麼量

- 機器：AMD Ryzen 5 3500X（6 核）、Windows 10、MSVC Release。是開發機，不是月月的 DAW 機；絕對毫秒數換機器會變，**比例**（32 比 16、和 10.667 ms 預算比）才是可帶走的部分。
- 搶音：沿用 WF1002-C1 的「雙胞胎」法（程序內的 `juce::Synthesiser`，接線和外掛建構子一模一樣）。**驗證雙胞胎＝真外掛**：用 16 建的 VST3 輸出 vs 雙胞胎(16)，與用 32 建的 VST3 輸出 vs 雙胞胎(32)，四個測例每一次 `max|差| = 0`（逐樣本相同）。
- 負載：每個區塊用高精度計時器量處理時間。「雙胞胎(只有合成器)」每種 pool 每個測例重複 5 次（全新合成器）；「VST3」是真二進位含整條效果鏈。整套 HostProbe 跑 3 輪（16、32 交錯），另用最終版二進位再各確認 1 輪。
- 測例：給愛麗絲鋼琴版（最多 12 顆）、月光第一樂章舌鼓版（最多 20 顆，已知最壞的真曲子）、**壓力測試**＝32 個不同音高同時按住 3 秒（這是 32 顆 pool 最多能對一個引擎提出的負載；這是合成的，不是樂譜），Chromatic（舌鼓）與 Piano 各一。
- **沒量到的**：FM 引擎（HostProbe 沒有 FM 雙胞胎；pool 常數也會影響 FM，FM 的負載沒有量）、把外掛放進 DAW 與其他音軌一起跑的情形、pool 變大的記憶體。

## 5. 對照判準

| 判準 | 結果 | 說明 |
|---|---|---|
| **C1 搶音減半** | **通過** | 月光舌鼓版 64 → 0（被搶的還按著的音 4 → 0） |
| **C2 沒有即時違規** | **不通過** | (a)月光 0 違規、(d)真 VST3(32) 月光 0 違規、壓力 Chromatic 0 違規：都過。**壓力 Piano 在 32 每次重複都有 148～153 個區塊（約三成）≥ 預算**，真 VST3 也一樣（3 輪 448 個）。另外嚴格照字面，給愛麗絲(32) 30 次重複裡出現 3 個違規區塊，但那是排程雜訊（上表 ※），不是這條不通過的原因 |
| **C3 餘裕 ≤ 預算一半** | **不通過（但不是決定性證據）** | 照事先寫的字面，連 pool 16 的給愛麗絲、月光都有單一區塊超過 5.33 ms（最差 7.49 ms）：「最慢的單一區塊」會被作業系統偶發尖峰污染，這個判準的量法選得不好。我**沒有**事後改判準；結論不靠它，靠 C2 的壓力 Piano（平均就占預算 68%、p99 是預算 1.9 倍，不是偶發） |
| **C4 沒有附帶改變** | **通過** | 給愛麗絲：16 與 32 輸出 `max\|差\| = 0`；CLI 不共用 pool（§1） |

**結論：維持 16。** 原因寫成一句：32 顆 Piano 同時響時，一個區塊要 7.3 ms（平均）～20.5 ms（p99），超過 10.67 ms 的即時預算，約三成區塊來不及；而 32 顆 pool 的好處（月光舌鼓版不再被搶）只在 Chromatic 引擎這種輕量 voice 上有，同一個 pool 數字卻也套在 Piano 上。

## 6. 順便看到的（不是本卡要修的）

1. **現行 16 顆也已經貼著邊**：壓力 Piano（16 顆低音區鋼弦同時響）在 16 時 p99＝10.5 ms（預算 10.67 ms），30 次重複合計 107 個區塊超預算、真 VST3 3 輪 14 個。這代表「16 顆」本身在 Piano 引擎低音區滿載時，這台機器上就快來不及了——**這跟 pool 大小無關，是 Piano voice 本身的成本**（每顆約 0.15 ms／區塊）。已有的主張域 §10 沒有寫這一點；建議之後列入已知限制（需月月裁要不要）。
2. **Chromatic 引擎很輕**：32 顆舌鼓同時響，平均只占預算 4%、最慢占 19%。

## 7. 沒採用、但數字支持的選項（需要月月另裁，本卡沒做）

- **按引擎設不同大小**：Chromatic 32、Piano／FM 維持 16。月光舌鼓版的搶音問題（唯一已知會超過 16 的真曲子）只在 Chromatic，而 Chromatic 32 顆滿載的數字（上表）過得了 C2、也離 C3 很遠。但這會把主張域 §10「每個引擎 16 顆」改成「依引擎」，是新的裁決題，而且 FM 引擎沒量；本卡不擅自做。
- 如果之後要再試加大：先量 Piano 的每顆成本（降 voice 負載比加 pool 更根本），再重跑本卡的方法（`wf1003_V_method.txt`）。
